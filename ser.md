Архитектура облачного GPU-инференса по API
Цель: создать универсальную инфраструктуру для размещения примерно 10 open-source нейросетей с Hugging Face. Модели доступны через API для подключения любых сайтов, приложений и AI-агентов через MCP.

Главный принцип: CPU-инфраструктура работает постоянно, GPU запускается только при поступлении задач. При увеличении нагрузки автоматически запускаются дополнительные GPU Worker.

3. Организация моделей
Не создаём отдельный Docker-образ для каждой модели. Группируем по совместимости библиотек и требованиям к GPU.
Образ	Примеры моделей
Diffusers	FLUX, SDXL, SD 3.5
Video	Wan, HunyuanVideo
Audio	Whisper, TTS
Custom	Нестандартные модели

Ориентировочно 2–4 образа для 10 моделей.

Если модели несовместимы по версиям библиотек или требованиям к VRAM, разделяем их.

Почему: меньше Docker-сборок, проще обновление и обслуживание.
4. Хранение моделей
Используем RunPod Cached Models для Hugging Face.
- В Docker храним код и библиотеки.
- В кэше находятся веса моделей.
- При запуске Worker веса доступны локально, если подходящий кэшированный хост найден.
- Модель загружается в VRAM при запуске Worker.
- Повторное скачивание из HF при каждом запросе не требуется.
Важно: кэш весов не означает постоянное хранение модели в VRAM. Загрузку в видеопамять всё равно нужно учитывать при cold start.

Если Cached Models не подходит, используем Network Volume.

Документация: RunPod Cached Models.
5. Принцип работы API
Предоставляем единый API для всех моделей.

POST /v1/jobs
{
  "model": "flux-dev",
  "input": {
    "prompt": "A cinematic landscape",
    "width": 1024,
    "height": 1024
  }
}


Ответ:
{
  "job_id": "uuid",
  "status": "queued"
}


Проверка:

GET /v1/jobs/{job_id}

Ответ:
{
  "job_id": "uuid",
  "status": "succeeded",
  "result": {
    "url": "https://storage.example/result.png"
  }
}


Также предусматриваем:
- Webhook для уведомления о завершении.
- Отмену задач.
- Статусы queued, processing, succeeded, failed.
- API-ключи для клиентов.
- Лимиты и учёт стоимости.
Почему асинхронный API: генерация изображений и особенно видео может занимать минуты. Пользователь не должен держать HTTP-соединение открытым.
6. Масштабирование
Настройки RunPod:
Параметр	Стартовое значение
Minimum Workers	0
Maximum Workers	1–2
GPU на Worker	1
Execution Timeout	По модели
Idle Timeout	По результатам тестов

При отсутствии задач Worker выключаются. При росте очереди RunPod запускает дополнительные Worker.

Не создаём GPU-сервер через API для каждой задачи: Serverless уже решает эту задачу.
7. Что не используем на старте
- Kubernetes — избыточная инфраструктура.
- Собственный GPU Scheduler — уже есть у RunPod.
- Redis/BullMQ — пока достаточно очереди провайдера.
- Отдельный образ для каждой модели — лишнее обслуживание.
- Постоянно работающие GPU — лишние расходы.
- Собственный GPU-сервер — пока нет необходимости.
8. План реализации
1. Инвентаризировать 10 моделей: зависимости, VRAM, лицензии, время загрузки.
2. Собрать первый Docker Worker.
3. Создать RunPod Serverless Endpoint.
4. Подключить Cached Models.
5. Реализовать API Gateway и Task Manager.
6. Проверить полный цикл выполнения задачи.
7. Добавить остальные модели и Endpoint.
8. Провести нагрузочные тесты и настроить лимиты расходов.
9. Внешний доступ
Инфраструктура должна предоставлять независимый от клиентского приложения интерфейс.
- REST API — для сайтов и приложений.
- MCP Server — для подключения AI-агентов.
- API Keys — идентификация и контроль доступа.
- Webhooks — получение результатов.
- Usage API — статистика использования и расходов.
В итоге любой разработчик сможет подключить модель к своему сайту или агенту, не занимаясь GPU, Docker, PyTorch и Hugging Face.

Итоговый выбор: RunPod Serverless Flex + Python Workers + TypeScript API Gateway + Hugging Face Cached Models. Начинаем с одного Worker и одной модели, затем расширяем инфраструктуру до остальных.
